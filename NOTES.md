# Shelved: shader cache v2 read errors

This branch is shelved on purpose; no PR was opened, and it should not be reopened without answering the points below. It makes the v2 log reader report a read that failed partway, and makes the driver blob store and compaction refuse to act on such a read. Review showed the trade is worse than upstream's design for files that are caches. A persistent read error (a bad sector, a mount that returns EIO) would turn the driver blob store off on every boot and fail every compaction forever, where upstream starts the file over or rewrites it without the unreadable tail, which heals itself. A held lock is not exclusive on every file system (NFS, SMB, some FUSE mounts), so the strict rule can report a file that only shrank as a read error. The store's constructor now waits up to 5 s for the lock on the boot path, uncancellable, and holds it through the whole read, where upstream takes no lock unless it is about to remove the file. A race remains (HasBytesOnDisk is a second stat after the read), and on libstdc++ a tolerant read that hits an error keeps nothing of the failing chunk. Each point has an answer, but every answer adds machinery to upstream's deliberate "tolerant, rebuild" choice for a transient I/O error. The part that was clearly right, the precompiled store keeping its state (with the /dev/null test), went in separately.
